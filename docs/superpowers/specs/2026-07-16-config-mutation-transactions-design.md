# 配置修改事务一致性设计

## 目标

为平台所有会修改主配置文件的 HTTP 操作建立同一套进程内事务边界，防止资源、自动恢复、自动备份、证书续期、改密和账号管理并发执行时发生以下问题：

- 两个请求都从旧快照读取配置，后保存的请求覆盖先保存请求的成功修改。
- 多个线程同时写入固定的 `.json.tmp` 文件，导致临时文件争用、替换失败或内容交叉。
- 请求在鉴权后等待锁，期间账号被禁用、降级、删除或会话失效，但旧请求仍按过期权限修改配置。
- 配置保存、运行态重置和审计日志的顺序不可预测，难以判断成功响应对应的最终状态。

本批只保证单个应用进程内由平台代码发起的配置修改不会互相覆盖。人工编辑、另一个独立应用进程或不使用平台事务模块的外部脚本仍需要停写窗口或后续跨进程锁支持。

## 当前写路径

需要纳入共享事务的函数固定为：

- `backend/resources.py`
  - `persist_resource_record()`
  - `persist_resource_deletion()`
  - `persist_resource_acknowledgement()`
- `backend/settings.py`
  - `persist_auto_recovery_enabled()`
  - `persist_auto_backup_enabled()`
  - `persist_cert_renewal_enabled()`
- `backend/auth_api.py`
  - `change_password_payload()`
- `backend/accounts_admin.py`
  - `upsert_account_user_payload()`
  - `delete_account_user_payload()`

`account_users_payload()`、登录、会话查询、退出、锁定列表和审计查询不修改主配置，不进入本批写事务。

## 一致性模型

平台提供“单进程可串行化”的配置修改语义：

1. 同一时刻最多一个配置修改事务执行。
2. 每个事务在取得锁后重新读取最新原始配置。
3. 涉及账号或操作权限的请求在锁内使用最新配置重新鉴权。
4. 校验、读改写、原子替换、运行态同步和对应操作日志按固定顺序完成后才释放锁。
5. 失败请求不得保存部分内存修改；保存前失败不改变磁盘配置。
6. 配置已经成功替换但后续日志失败时，响应必须明确说明“配置已保存、日志失败”，不能伪装为完整回滚。

这不是数据库事务：配置文件、恢复日志、账号审计日志和内存运行态位于不同介质，无法提供跨介质原子回滚。本批保证配置不会丢更新，并让部分成功语义可见、可测试。

## 分层设计

### 共享事务模块

新增 `backend/config_transactions.py`，只负责配置修改并发控制：

```python
from contextlib import contextmanager
from functools import wraps
import threading

_CONFIG_MUTATION_LOCK = threading.RLock()

@contextmanager
def config_mutation_transaction():
    with _CONFIG_MUTATION_LOCK:
        yield

def serialized_config_mutation(operation):
    @wraps(operation)
    def synchronized(*args, **kwargs):
        with config_mutation_transaction():
            return operation(*args, **kwargs)
    return synchronized
```

必须使用 `RLock`：HTTP 路由需要在“锁内重新鉴权”后调用已由装饰器保护的领域函数，形成同线程嵌套事务；普通 `Lock` 会在这种调用链中死锁。

### 配置文件写入

`backend/config.py::save_config_raw()` 也必须进入同一个可重入事务，并改为：

- 在目标目录创建每次调用唯一的临时文件。
- 使用 UTF-8 写入完整 JSON 和结尾换行。
- `flush()` 后执行 `os.fsync()`，再关闭临时文件。
- 使用 `os.replace()` 原子替换目标文件。
- 任意异常时尽力删除本次临时文件，不能删除其他线程或其他进程的临时文件。

唯一临时文件解决固定 `.json.tmp` 的名称争用；共享锁解决单进程内的读改写丢更新。两者缺一不可。

### 领域函数

九个配置修改函数统一使用 `@serialized_config_mutation`。现有资源模块私有 `_resource_transaction_lock` 和 `_serialize_resource_transaction` 删除，避免形成彼此独立的锁域。

每个函数的锁内顺序为：

1. 读取最新原始配置。
2. 对最新配置执行重复项、目标存在性、动作安全、账号角色和密码策略校验。
3. 只修改内存副本。
4. 保存配置文件。
5. 更新与该配置直接相关的运行态。
6. 追加恢复日志或账号审计日志。
7. 构造响应并释放锁。

### 锁内重新鉴权

账号改密和账号管理函数不得只信任路由进入前加载的 `config`：

- 取得事务锁后读取 `raw_config`。
- 使用请求中的会话令牌对 `raw_config` 重新执行会话和角色校验。
- 后续密码、当前账号、自锁保护和“至少一个管理员”检查全部基于同一个 `raw_config`。
- 新会话令牌使用保存后的最新配置和会话密钥生成。

资源和三个设置路由在进入领域写函数前同样需要锁内重新加载配置并重新鉴权。为避免无凭据请求占用事务锁，允许先做一次快速鉴权；真正授权决定以锁内复核结果为准。

## 锁粒度和性能

配置写请求频率很低，持锁时间主要是一次小型 JSON 文件读写和一条本地日志写入。使用单一全局锁比按资源、账号或设置拆锁更正确，因为所有领域最终替换的是同一个文件。

监控轮询、Dashboard 读取和 Prometheus 查询不取得写事务锁。原子替换保证普通读取只看到旧完整文件或新完整文件，不会看到半写文件。

## 异常处理

- JSON 解析、业务校验和鉴权失败：不调用保存函数。
- 临时文件写入、`fsync` 或替换失败：保留原配置，清理本次临时文件，返回固定安全错误。
- 配置保存成功、运行态更新失败：返回明确部分成功错误，并让下一轮 Dashboard 从磁盘重新收敛。
- 配置保存成功、日志失败：保留配置，返回现有“已保存但日志失败”语义。
- 任意异常都必须通过上下文管理器释放锁。

## 测试策略

新增 `tests/test_config_transactions.py`，使用 `threading.Barrier`、`Event` 和受控内存存储，不使用依赖调度时机的 `sleep`：

- 资源新增与自动备份开关并发，最终两项修改都存在。
- 资源新增与账号新增并发，最终资源和账号都存在。
- 改密与证书续期开关并发，密码哈希和证书配置都存在。
- 账号在请求等待锁期间被禁用或降级，等待中的旧请求在锁内复核后被拒绝。
- 保存函数为连续调用生成不同临时文件，异常后无残留临时文件。
- 一个事务抛出异常后，后续事务仍能取得锁并成功。
- 装饰器保留函数名、模块归属和测试注入能力。

最后运行聚焦测试、全量测试和真实 HTTP 设置拒绝路径。测试不得修改真实私有配置。

## 验收标准

- 所有主配置写路径共享同一个可重入锁。
- 不再存在资源专用锁或其他互不相干的配置写锁。
- 跨领域并发成功请求不会丢失任一修改。
- 等待锁期间发生权限变化时，旧凭据不能继续修改配置。
- 固定 `.json.tmp` 被唯一临时文件替代，异常清理只处理本次文件。
- 现有领域测试、并发测试和全量回归全部通过。
- README 和桌面中文总览准确记录保证范围与跨进程限制，桌面文档不包含代码同步信息。

## 不在本批范围

- 多个独立应用进程同时修改同一配置文件的完全串行化。
- 为人工编辑提供在线合并或冲突解决界面。
- 把 JSON 配置迁移到数据库。
- 对恢复日志和账号审计日志提供跨文件原子回滚。
